# W01 — Open and refresh a saved Plan Package

## Goal and inputs

Provide a reusable local application that opens two saved packages, makes their phases, criteria and designs inspectable, and refreshes complete edits without publishing mixed content. Probe native annotation compatibility early and report actual limitations.

Source: [selected W01 brief](../../../project_status.md#selected-planning-brief--w01), [repository conventions](../../../README.md#planning-and-execution-conventions), package [minimum content](../../specs/01-plan-package.md#minimum-content), [phase semantics](../../specs/01-plan-package.md#phase-meaning-and-dependencies), [references](../../specs/01-plan-package.md#references-and-identity), [visual meaning](../../specs/01-plan-package.md#visual-meaning), and [representative example](../../specs/01-plan-package.md#representative-example). Viewer requirements: [components](../../specs/02-viewer-and-review.md#reusable-components), [boundaries](../../specs/02-viewer-and-review.md#application-boundaries), [coherence](../../specs/02-viewer-and-review.md#coherent-file-updates), [native loop](../../specs/02-viewer-and-review.md#native-annotation-loop), [isolation](../../specs/02-viewer-and-review.md#assets-and-isolation), and [performance](../../specs/02-viewer-and-review.md#performance-and-proportionality).

Non-goals: implementing offline exercise persistence itself; acceptance records, retained acceptance/history UI or revision comparison; execution context CLI; skill changes; SGM integration; hosting, accounts, database, custom feedback transport or agent-session management. W02–W05 remain outside this plan.

## Engineering decisions

Use one npm project with TypeScript, a Node local service, React with Vite for the viewer, Vitest for core/runtime checks and Playwright for browser behavior. Choose and lock mutually compatible supported versions during P1; no dependency installation occurs during planning. Use `src/core`, `src/server`, and `src/viewer`, with `examples/offline-recovery` and `examples/save-outcome`. Core has no browser, HTTP, or Node filesystem dependency: it accepts parsed data and a supplied reference resolver. The server owns filesystem access, validation orchestration, immutable loaded bytes, HTTP and watch events. The viewer consumes the resolved model, never reparses a competing format. An optional thin presentation adapter reuses the viewer.

### Supported package contract

Support versioned `plan.json` with inline phases only. Preserve the spec's example fields for identity, revision, Markdown goal, scope, constraints, phases, criteria and dependencies. Add typed references, assets, decisions and questions with stable IDs, explicit purpose/applicability, and blocking scope. Assets declare authority and format; questions identify affected phases. Document the exact supported fields and examples in implementation documentation. Reject unsupported format versions and declared required capabilities, duplicate addressable IDs, unknown dependencies/applicability targets and cycles with item/path diagnostics. Unknown optional metadata can be retained without implying support. Structural validity never implies acceptance or execution readiness.

References explicitly select package, repository or external roots. Local required material must resolve; optional missing material yields a visible diagnostic. External links declare purpose and access requirements; W01 does not fetch external content. A required external input cannot be reported as resolved and must have a local retained copy for a fully resolved candidate. No current-working-directory-relative interpretation is allowed.

Use `plan.json` as the final publication manifest. It declares SHA-256 digests for every local file consumed in the view, including selected assets and their transitive dependencies. Narrative is inline; local reference/asset bytes are loaded and checked against this inventory. Every file edit, including an asset-only edit, ends by atomically replacing `plan.json` with updated digests and an incremented author revision. Provide a local publication helper that validates and computes the manifest, writes a sibling temporary file, then renames it; this operation does not mean acceptance. Detect changes to a manifest during resolution by reading its bytes before and after candidate loading. Validate the complete candidate before swapping it into service.

Compute a separate displayed content ID from exact manifest bytes and verified file digests. Serve all model and asset responses through that immutable loaded candidate ID, from captured bytes rather than rereading working files. Retain candidates used by connected views; a bounded cache may evict older ones, but evicted URLs must fail explicitly and never serve newer bytes. This prevents an old page from displaying a newer prototype during an interrupted edit. History across restart is outside W01.

### Runtime and presentation

Bind to loopback and serve only explicitly selected packages/repository roots. Validate decoded paths and real paths, including symlinks, on every candidate load; reject escapes and undeclared dependencies. Provide package/model and candidate-scoped asset endpoints plus server-sent events for new candidates, diagnostics and connection recovery. No write API is needed. Browser selection is keyed by package ID and stable item ID; show author revision, content ID, draft state and stale/disconnected status as text.

Render Markdown with raw HTML disabled and safe link protocols. Display SVG as images rather than injecting markup into the shell. Isolate HTML mock prototypes in sandboxed frames with scripts permitted only for the demonstration, without same-origin, navigation or privileged API access. Serve declared relative dependencies under the same candidate prefix and use restrictive content policies; reject unsupported dependency loading with an explicit limitation. Controls and simulated outcomes in the sample must be visibly labeled as mock behavior.

## Verification intent

P2 depends on P1's resolved model and file-serving contract; P3 depends on P2's navigation and candidate-bound rendering. P1 establishes `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build`; P2 adds `npm run test:e2e`. After documented initial setup, `npm run dev -- --package examples/offline-recovery` must be the single launch command, with no separate manually started service. Document browser-test installation separately. Each phase runs its applicable checks before claiming verification; CI is not required. Host feedback and performance measurements require explicit evidence beyond passing automated checks.

## P1 — Package core and coherent initial loading

Objective: load either example into one validated, byte-consistent model through a confined local runtime.

- **P1-T1:** Establish the project, scripts, core/server boundaries, documented inline format and publication helper. Implement validation, ID/reference lookup, applicable obligations and blocking-question diagnostics. Keep structural validity and unresolved material distinct.
- **P1-T2:** Author the complete offline-recovery package with two substantive phases: persistence outcomes/restore/discard, then recovery experience. Include saved-only-after-success, failed-write preservation, explicit invalid-snapshot unavailability, and protection against queued saves resurrecting discarded progress. Carry consumer-required result distinctions into the first phase. Add a structured phase map, linked explanatory behavior diagram, selected interactive recovery mock with local dependencies, and a nonblocking wording question. Create an independently worded one-phase save-outcome package. These are illustrative proposals, never evidence that an exercise application was implemented.
- **P1-T3:** Implement candidate loading, digest checks, manifest reread, immutable asset serving, path confinement and actionable diagnostics. Expose a minimal runtime model interface for P2; do not add a parallel CLI semantics engine.
- **P1-T4:** Verify malformed JSON, duplicate IDs, cycles, missing targets/files, unsupported required semantics, unresolved questions, digest mismatch, manifest mutation during loading, traversal and symlink escapes. Test that asset responses remain bound to captured bytes after filesystem mutation. Document format, author publication procedure and launch/setup commands.

Acceptance: both fixtures load from a different working directory using declared roots; all required local content resolves; failures identify affected paths/items; incomplete initial content produces diagnostics without a valid-revision claim. Tests demonstrate that neither mixed bytes nor out-of-root files can be served. Established typecheck/lint/unit/build checks pass. The offline example's full obligations and mock labels receive manual content review.

## P2 — Reusable viewer and native-surface probe

Objective: inspect the same model through an accessible browser UI and establish the available host presentation path before refresh work.

- **P2-T1:** Implement plan header, overview, stable phase navigation, exact criterion list, decisions/questions and artifact frames. Keep the goal and shared constraints available from phase views. Generate clickable dependency maps from structured relationships. Link the explanatory diagram to its governing criteria. Show asset purpose, authority, revision and mock label; do not imply evidence where none exists. Deep links resolve package/item IDs and handle missing targets explicitly.
- **P2-T2:** Integrate safe narrative rendering and isolated candidate-scoped prototypes. Verify keyboard navigation, visible focus, wrapped paths, desktop/tablet hierarchy and narrow-screen stacking. Use the second fixture to expose hard-coded sample assumptions.
- **P2-T3:** As soon as the initial viewer renders, inspect the actual environment's supported host presentation capabilities and attempt a minimal meaningful annotation against a visible criterion/design and revision. Record mechanism, environment, whether feedback actually reaches the agent, and payload fields available for attribution. Where human annotation is necessary, request that concrete interaction during execution. A localhost page, iframe or custom attribute alone is insufficient evidence. If unsupported or the interaction is unavailable, record the exact limitation and keep browser viewing usable; do not build replacement feedback transport. If feedback arrives, map it only to a clearly identified item/revision and demonstrate an authoritative package edit via the publication path, with manual reload at this phase.
- **P2-T4:** Add browser checks for both packages, phase/criterion links, designs, blocking labels, unsafe narrative and prototype isolation. Inspect representative desktop/tablet/narrow layouts and retain relevant evidence in execution results. Document the host probe outcome and any supported adapter's refresh limitations.

Acceptance: both packages render from their data with navigable phases, criteria and applicable designs; the mock is usable inside its declared boundaries and cannot operate privileged viewer controls. Standard checks plus browser tests pass. Host compatibility is either demonstrated by actual received feedback or explicitly recorded as unavailable/unverified with evidence; the fallback is not reported as a successful annotation trial.

## P3 — Live refresh, recovery and measured behavior

Objective: publish complete changes automatically while preserving useful navigation and exposing failures.

- **P3-T1:** Watch only manifests, declared files and necessary parent directories for rename/missing-file recovery. Debounce for efficiency, but rely on manifest/digest validation for correctness. Serialize or generation-fence concurrent loads so a slow older candidate cannot replace a newer publication. Rediscover declared watch targets after valid updates. Retry on subsequent writes and reconnect; avoid endless hot-loop retries for invalid files.
- **P3-T2:** Publish successful candidate events atomically and show rejected-candidate diagnostics alongside the last valid revision. On reconnect fetch current runtime state, including diagnostics, rather than relying on missed events. Handle server restart and unavailable old candidate IDs explicitly. Preserve selected phase/item, scroll anchor and expanded details where surviving IDs permit; on removal choose the surviving phase or overview and explain the change.
- **P3-T3:** Exercise valid text and asset edits, interrupted multi-file saves, atomic renames, missing files, persistent invalid JSON, corrected edits, rapid overlapping saves, selected-item deletion, newly declared dependencies and disconnect/reconnect. Assert through browser-visible model and asset content that no mixed candidate is published and that last-valid/stale labels remain honest. Include an initially invalid package that becomes valid without restarting.
- **P3-T4:** Measure warm package opening, parse/load, render and data/asset refresh separately over at least five ordinary runs of the representative fixture. Record machine/runtime/browser, fixture sizes, method, range and median, separating dependency setup, server startup and all agent time. Investigate repeatable times beyond a few seconds; document a concrete unresolved performance finding if not resolved. Finish usage/troubleshooting documentation and independent phase verification.

Acceptance: all update scenarios recover without restarting the viewer; surviving navigation remains stable; removed targets fall back visibly. Complete edits show the new content ID and matching assets, rejected edits retain the prior ID with diagnostics, and reconnect restores current state. Standard and browser checks pass. Results include measured local performance and the native probe's actual status, not an inferred host capability or general planning-speed claim.

## Prerequisites, open issues and rollback

Execution needs an available supported Node/npm toolchain, dependency access, and a local browser. Verify these at execution start and record access limitations. Routine exact versions and visual styling are delegated to execution within these boundaries.

The only intentionally unresolved capability is actual native annotation presentation and payload shape, resolved by P2's probe; it does not block the browser path. No product-design question blocks beginning P1. If the isolation model cannot support a selected prototype dependency, make the limitation visible and resolve its packaging without weakening filesystem or browser boundaries.

There is no existing application or persistent user data to migrate. Invalid updates are rolled back operationally by retaining the last valid in-memory candidate; restoring and republishing known-good package files recovers after restart. This is not durable accepted-plan recovery, which remains W02 scope.
